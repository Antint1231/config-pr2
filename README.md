# Визуализатор графа зависимостей (Alpine Linux, apk)

Практическая работа № 2, вариант 19.
Дисциплина «Конфигурационное управление», группа ИКБО-11-25.

## 1. Общее описание

Консольная программа на Python 3 строит граф зависимостей пакета
Alpine Linux (формат apk) и выводит его на языке диаграмм Mermaid. Список
пакетов берется напрямую из файла `APKINDEX.tar.gz` репозитория, без
использования `apk`, `pip` и сторонних библиотек для разбора пакетов
(сторонняя библиотека PyYAML нужна только для чтения конфигурации).

Возможности:

- настройка через YAML-файл;
- прямые и транзитивные зависимости, обход в ширину (BFS) с рекурсией;
- ограничение глубины и фильтр по подстроке в имени пакета;
- корректная работа с циклическими зависимостями;
- тестовый режим: граф берется из текстового файла, пакеты называются
  большими латинскими буквами;
- вывод зависимостей в виде ASCII-дерева;
- вывод порядка загрузки пакетов;
- вывод графа на языке Mermaid.

Структура проекта:

```
src/main.py        точка входа
src/config.py      чтение и проверка YAML-конфигурации
src/apk_repo.py    скачивание и разбор APKINDEX (формат apk)
src/file_repo.py   тестовый репозиторий из файла
src/graph.py       построение графа (BFS) и порядок загрузки
src/visual.py      Mermaid и ASCII-дерево
src/errors.py      классы ошибок
tests/             модульные тесты
examples/          примеры конфигураций и тестовых репозиториев
```

## 2. Описание функций и настроек

### Настройки (YAML-файл)

| Параметр           | Тип    | По умолчанию | Описание                                  |
|--------------------|--------|--------------|-------------------------------------------|
| `package`          | строка | обязательный | имя анализируемого пакета                 |
| `repository`       | строка | обязательный | URL репозитория или путь к тестовому файлу |
| `test_mode`        | bool   | `false`      | `true` - читать граф из файла             |
| `ascii_tree`       | bool   | `false`      | дополнительно вывести ASCII-дерево        |
| `max_depth`        | целое  | `3`          | максимальная глубина анализа (>= 0)       |
| `filter_substring` | строка | пустая       | пакеты с этой подстрокой в имени пропускаются |
| `load_order`       | bool   | `false`      | дополнительно вывести порядок загрузки    |

Пример: `examples/config_apk.yaml`. Для `repository` указывается адрес
каталога репозитория, например
`https://dl-cdn.alpinelinux.org/alpine/latest-stable/main/x86_64`
(к нему добавляется `/APKINDEX.tar.gz`).

Глубина 0 - только сам пакет, 1 - пакет и его прямые зависимости и т. д.
Корневой пакет анализируется всегда, даже если его имя содержит
подстроку фильтра.

### Формат тестового репозитория

Каждая строка - один пакет: `A: B C` (A зависит от B и C). Пустые строки и
строки с `#` пропускаются. Имена - только большие латинские буквы, все
зависимости должны быть описаны в файле. Примеры: `examples/repo_basic.txt`,
`examples/repo_cycle.txt`.

### Основные функции

- `config.load_config(path)` - читает YAML и проверяет параметры.
- `apk_repo.load_apk_repo(url)` - скачивает APKINDEX и разбирает поля
  `P` (имя), `D` (зависимости), `p` (provides). Условия версий
  (`>=`, `=`, `~`) отбрасываются, зависимости вида `so:...` и `cmd:...`
  заменяются на пакет, который их предоставляет, зависимости `!имя`
  (конфликты) пропускаются.
- `file_repo.load_file_repo(path)` - читает тестовый репозиторий.
- `graph.build_graph(repo, root, max_depth, substring)` - BFS с рекурсией:
  каждый вызов обрабатывает один уровень и вызывает себя для следующего.
  Уже посещенные пакеты повторно не обходятся, поэтому циклы не приводят
  к зависанию (ребро в цикле сохраняется).
- `graph.load_order(graph, root)` - порядок загрузки (зависимости раньше
  зависящих от них пакетов).
- `visual.to_mermaid(graph)`, `visual.to_ascii_tree(graph, root)` - вывод.

## 3. Сборка и запуск тестов

Сборка не нужна. Требуется Python 3.8+ и PyYAML:

```
pip install -r requirements.txt
```

Запуск программы:

```
./run.sh config.yaml
python3 src/main.py examples/config_test.yaml
make run CONFIG=examples/config_cycle.yaml
```

Запуск тестов:

```
make test
```

## 4. Примеры использования

### Этап 1. Параметры и обработка ошибок

Все ошибки выводятся одной строкой с префиксом «Ошибка:», код возврата 1.

```
$ cat config.yaml
  package: A
  repository: examples/repo_basic.txt
  max_depth: abc
$ python3 src/main.py config.yaml
Ошибка: параметр 'max_depth' должен быть целым числом

$ cat config.yaml
  repository: examples/repo_basic.txt
$ python3 src/main.py config.yaml
Ошибка: не задан обязательный параметр 'package'

$ cat config.yaml
  package: A
  repository: ftp://site/repo
$ python3 src/main.py config.yaml
Ошибка: параметр 'repository' должен быть URL (http:// или https://)

$ cat config.yaml
  package: A
  repository: nofile.txt
  test_mode: true
$ python3 src/main.py config.yaml
Ошибка: файл тестового репозитория не найден: nofile.txt

$ cat config.yaml
  package: A
  repository: examples/repo_basic.txt
  color: red
$ python3 src/main.py config.yaml
Ошибка: неизвестный параметр 'color'

```

В первых версиях программа печатала параметры в виде ключ-значение
(`package: A`, `max_depth: 3`, ...); по заданию это нужно было только на
этапе 1, поэтому в итоговой версии этот вывод убран (смотрите историю
коммитов).

### Этап 2. Прямые зависимости (настоящий репозиторий)

Прямые зависимости берутся из поля `D` записи пакета в APKINDEX. Проверка
выполнялась на локальном HTTP-сервере с файлом `APKINDEX.tar.gz` в
настоящем формате (доступ к dl-cdn.alpinelinux.org из среды разработки был
закрыт). Пример для репозитория Alpine:

```
$ ./run.sh examples/config_apk.yaml
```

### Этап 3. Граф, глубина, фильтр, циклы (тестовый режим)

Репозиторий `examples/repo_basic.txt`:

```
A: B C
B: D
C: D E
D: F
E:
F:
G: H
H:
```

В итоговой версии граф выводится на Mermaid (этап 5); для наглядности
ниже показан только блок ASCII-дерева.

**Полная глубина** (`max_depth: 10`):

```
A
├── B
│   └── D
│       └── F
└── C
    ├── D (уже показан)
    └── E
```

**Глубина 1** (`max_depth: 1`):

```
A
├── B
└── C
```

**Фильтр** `filter_substring: "D"` (пакет D и все, что доступно только через него, исключены):

```
A
├── B
└── C
    └── E
```

**Цикл** (`examples/repo_cycle.txt`: A -> B -> C -> A, D -> D):

```
A
└── B
    ├── C
    │   └── A (цикл)
    └── D
        ├── D (цикл)
        └── E
```

Во всех случаях программа завершается, цикл помечается `(цикл)`.

### Этап 4. Порядок загрузки

Для `examples/repo_basic.txt`, пакет A:

```
Порядок загрузки для пакета A:
  1. F
  2. D
  3. B
  4. E
  5. C
  6. A
```

Для `examples/repo_cycle.txt`, пакет A (есть цикл):

```
Порядок загрузки для пакета A:
  1. C
  2. E
  3. D
  4. B
  5. A
```

Порядок строится обходом в глубину: пакет добавляется в список после всех
своих зависимостей. Обратное ребро цикла игнорируется.

**Сравнение с реальным менеджером пакетов.** Для сравнения используется
`apk add --simulate <пакет>` в контейнере Alpine (например,
`docker run --rm alpine apk add --simulate nginx`). Результат может
отличаться, потому что:

1. `apk` не ставит пакеты, которые уже есть в системе (musl, busybox и
   др. входят в базовый образ), а программа показывает все зависимости.
2. `apk` использует все подключенные репозитории (main и community),
   программа читает только один репозиторий, а зависимости, которых в нем
   нет, остаются листьями графа.
3. `apk` учитывает ограничения версий, `install_if` и выбирает поставщика
   виртуальных зависимостей (provides) с помощью решателя. Программа
   версии игнорирует и берет первого найденного поставщика.
4. Порядок независимых друг от друга пакетов в `apk` определяется
   решателем, а у программы - порядком обхода в глубину, поэтому такие
   пакеты могут идти в другой последовательности. Главное правило
   (зависимость раньше зависящего пакета) выполняется в обоих случаях.
5. Программа ограничена `max_depth` и `filter_substring`, у `apk` таких
   ограничений нет.

### Этап 5. Визуализация (Mermaid и ASCII-дерево)

Используется `examples/repo_cycle.txt` и `ascii_tree: true`,
`load_order: true`. Описание графа на Mermaid можно вставить в
https://mermaid.live или в Markdown-блок с типом `mermaid`.

**Пакет A**

```
graph TD
    n0["A"]
    n1["B"]
    n2["C"]
    n3["D"]
    n4["E"]
    n0 --> n1
    n1 --> n2
    n1 --> n3
    n2 --> n0
    n3 --> n3
    n3 --> n4

A
└── B
    ├── C
    │   └── A (цикл)
    └── D
        ├── D (цикл)
        └── E

Порядок загрузки для пакета A:
  1. C
  2. E
  3. D
  4. B
  5. A
```

**Пакет B**

```
graph TD
    n0["B"]
    n1["C"]
    n2["D"]
    n3["A"]
    n4["E"]
    n0 --> n1
    n0 --> n2
    n1 --> n3
    n2 --> n2
    n2 --> n4
    n3 --> n0

B
├── C
│   └── A
│       └── B (цикл)
└── D
    ├── D (цикл)
    └── E

Порядок загрузки для пакета B:
  1. A
  2. C
  3. E
  4. D
  5. B
```

**Пакет D**

```
graph TD
    n0["D"]
    n1["E"]
    n0 --> n0
    n0 --> n1

D
├── D (цикл)
└── E

Порядок загрузки для пакета D:
  1. E
  2. D
```

**Сравнение со штатными инструментами apk.** В `apk` нет вывода в формате
Mermaid. Ближайшие штатные средства: `apk info -R <пакет>` (прямые
зависимости) и `apk dot <пакет>` (граф в формате Graphviz). Расхождения с
ними те же, что и в этапе 4 (версии, provides, несколько репозиториев,
уже установленные пакеты), а также:

- `apk dot` показывает зависимости в виде `so:`/`cmd:` и выбранных версий,
  а программа заменяет их на имена пакетов-поставщиков;
- для настоящего репозитория программа пропускает зависимость пакета
  от самого себя (например, когда пакет сам предоставляет нужный `so:`),
  а в тестовом репозитории такая петля сохраняется и видна как `D --> D`.
